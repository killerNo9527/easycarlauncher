# 0.9.2-m12 歌词补拉 + 日志刷屏治理

## 1. 现象

切歌后音乐卡有时停在「暂无歌词」，但歌确实有歌词；过一阵（或桌面重启）又自己好了。
需要判断是「我们取歌词的时机/频率不对」还是「音乐应用推送不及时」。

## 2. 结论：是**对方不补推**，我们的读取时机没错

用日志把时序钉死了（md3Music 6.2.0）：

```
metadata: title=向云端 hasLyric=false   ← 换歌瞬间推来的元数据，extras 里没有 lyricInfo
已连接 md3Music（Media3），title=向云端
（之后 30 秒内对方再没有推任何带歌词的元数据）
```

而**同一时刻**重新连一次会话，读回来就是完整的歌词：

```
补拉后：metadata: title=向云端 hasLyric=true
解析歌词：54 行（含翻译 0 行）
```

也就是说：它换歌时先把「还没加载完歌词」的元数据推给我们，等歌词（联网）加载好之后
**不会再补推一条**。而 Media3 的 `MediaController` 只是会话的观察者，缓存里没有就是没有 ——
不去主动要，界面就永远停在「暂无歌词」。这解释了为什么「有时」：歌的歌词加载慢的时候才会命中。

补充：media3 1.4.1 的 `MediaController` 没有 `requestMetadata()`（那是 MediaSession 侧的能力），
所以「要」的唯一手段就是**重连一次会话**（不打断对方播放，控制器只是观察者）。

## 3. 改动

### 3.1 歌词补拉（`music/MusicController`）

- 触发条件：正在播放 + 有歌名 + 歌词 0 行；
- 节奏：`600ms / 1.5s / 3s / 6s`（累计约 11 秒），每次重连会话；拿到歌词或换歌立刻清零；
- 最多 4 次就停 —— 「这首本来就没歌词」只会白试 11 秒，不会一直骚扰对方；
- 关键坑：重连后对方会补发一次 `isPlaying=true`，那不是用户按的播放。
  原先的清零逻辑会把它当成「又给了对方一次机会」，于是
  「补拉 → 重连 → 清零 → tick 又补拉」变成无限重连。现在用 `lastAttachAt` 排掉刚 attach 完 2 秒内的播放回调。
- 实测（连切 5 首）：5 次补拉全部拿到歌词，其中 4 首第 1 次就中，1 首第 2 次中；
  静置 15 秒不再有任何多余重连。

### 3.2 补拉期间不闪「暂无歌词」（`home/HomeFragment`）

`Snapshot` 新增 `lyricPending`（0 行且正在补拉）。此时歌词区**留白**而不是写「暂无歌词」，
1 秒内歌词到了直接显示。用户看不到中间那一帧假状态。

### 3.3 日志刷屏（顺带修的，排查时才发现的）

模拟器没有悬浮窗权限时 `MapMaskOverlay` 的 `addView` 必然失败，而 `show()` 被布局变化反复调用
（几何比对只在「已挂上」时有意义），于是变成每秒几十次重试 + 几十行 `BadTokenException`；
同时地图卡文案在 `addOnLayoutChangeListener` 里无条件 `setText`，触发
`requestLayout() improperly called ... during layout`。两者把 logcat 缓冲刷满，
**把我们自己的排查日志挤没了**（一开始误以为补拉没生效，其实是日志被淹）。

- `MapMaskOverlay`：失败后 8 秒内不再重试，同一种失败只记一行；
- `HomeFragment.renderMapCardFace`：加「状态指纹」去重，重复调用直接返回。

修复后同样的启动过程：刷屏日志从「每次布局几十行」降到 3 行，日志终于可读。

## 4. 验证

- 1920×1080 模拟器：连切 5 首，`补拉 5 / 解析歌词 5`，无 `暂无歌词` 停留；
- 切歌后 0.35 秒截帧：已是新歌歌词（不是空白、也不是「暂无歌词」）；
- 静置 15 秒：补拉计数不再增长（无自激重连）；
- 无崩溃、底栏与音乐卡状态一致。

## 5. 仍未解决

- 歌词本身加载失败/确实没有的歌：11 秒后仍显示「暂无歌词」（正确行为）；
- 长歌名截断、非当前歌词行单行省略（上一版遗留，未动）。
