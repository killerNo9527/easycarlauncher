# 0.9.0-m10 变更说明

> 构建 `0.9.0-m10`（versionCode 10）· 2026-11-01
> 产物 `app/build/outputs/apk/debug/app-debug.apk`
> 三件事：**右栏顶边对齐**、**删掉状态栏里的调试胶囊**、**瞬时功耗 + 行程卡接上数据层**（含数据源核对结论）。

---

## 1. 右栏第一张卡和地图卡顶边对不齐

### 现象
截图红圈里那一条：地图卡顶边和右边第一张卡的顶边差了一截，整列像往下掉。

### 根因
两处偏差叠在一起：

1. `fragment_home.xml` 里 `map_host` 用 `@dimen/status_bar_height`（38dp），
   右栏 `theme_content_container` 却用 `@dimen/content_padding_top`（39dp）——先差 1dp；
2. 更主要的是：**右栏第一张卡自己带着 8dp 的 `layout_marginTop`**。
   时间卡一关（本机默认就是关的，时间在状态栏上），音乐卡顶上来，那 8dp 还留着，
   于是整列比地图卡低 8dp。

实测（1920×1080 / 240dpi）：地图卡 `y=57`，右栏第一张卡 `y=71`。

### 改法
- `theme_content_container` 的 `marginTop` 改成 `@dimen/status_bar_height`，两边同一个基准；
  `content_padding_top` 这个 dimen 随之删除（全项目只有这一处引用）。
- `HomeFragment.applyCardSpacing()`：卡片显隐变化后，**按「谁是第一张可见卡」重新分配间距**
  ——第一张 `0`，其余 `@dimen/right_container_card_spacing`。用代码算而不是写死 XML，
  是因为卡片显隐是运行时可变的（设置页四个开关）。

实测改完：`57 / 57`，齐平。

## 2. 删掉「高德悬浮窗 · 已配置」

这是调试期留在右上角的胶囊，既不该出现在正式桌面，也是它自己把状态栏搞得不齐 ——
胶囊有 `paddingVertical=4dp` + 自己的背景，文字中心和左边 15sp 时钟的中心天然差半行。

- `activity_launcher.xml`：删 `status_hint`，删 `bg_status_chip.xml`（已无引用）；
- `LauncherActivity.renderStatusBar()`：删掉整段文案/配色逻辑，
  顺带把 `AmapPlusController.probe(this)` 每 15 秒一次的静态探测也去掉了（桌面不该周期性查包管理器）。

## 3. 状态栏新增瞬时功耗

设计上照着参照版本「菱粉桌面」的状态栏做：它左半边是「里程 / 电耗 / 挡位 / 电压」，
我们这张桌面不需要那么密，只在右端放一个 `⚡ 12.5 kW`：

```
10:29   11月1日 星期日                                   ⚡ 12.5 kW
```

- 纯文字 + 矢量闪电（`ic_bolt.xml`，用 `app:tint` 上色，日夜自动跟随），
  **不加深色底、不加内边距**——就是为了让基线和左边时钟严格对齐（第 2 节踩过的坑）；
- 数值 `text_primary` / 单位与图标 `text_secondary`（夜间 `text_tertiary` 太暗，实测对比度不够）；
- 读不到车辆数据显示 `--`，**不隐藏也不填 0**：参照版本也是 `--KM / --kWh` 的占位风格；
- 设置项「状态栏显示瞬时功耗」可关。

新增 `@dimen/status_power_icon_size`（16dp / 大屏 21dp）。

## 4. 数据源核对结论（重要）

### 参照版本是怎么拿数据的（实证）
把 `com.zzh.launcher50s.alpha`（菱粉桌面 3.3.1，百度加固）装到 adbtest 上跑起来抓 `logcat`，
直接指出了它的通道：

```
W CarServiceBinderPropertyClient: 车辆监听服务未就绪
W VehicleDataRepository: api_service_fallback reason=bridge_empty, propId=0x21405021, areaId=1
```

- 线程名 `vehicle-bridge` / `vehicle-data-receiver`，服务 `…launcher50s.wuling.ApiService`；
- 它按 **「属性 ID + areaId」** 轮询车辆数据，抓到的 ID 有
  `0x21405019 / 0x21405021 / 0x21405178`（vendor **INT32**）与 `0x2160e003`（vendor **FLOAT**），
  协议前缀 `0x21…` 就是 Android Automotive 里「VENDOR + INT32/FLOAT + GLOBAL」的组合；
- 读不到就走 `api_service_fallback`。

它的设置页还有「电量校正 / 总电量设置 / 动态纯电续航（本次行程 / 当日 / 近 50km…）」，
说明它的「平均电耗」是**电量差 × 总电量 ÷ 里程**推出来的，不是直接读一个「百公里电耗」属性。

### 我们这边
**核对结果：不一致 —— 我们原来根本没有数据源。**
`include_travel_card.xml` 里三格是写死的 `--`，`HANDOFF.md` 第 7 节自己也记着这条。

参照版本那套 binder 是主机厂私有的，APK 又加固，**拿不到 AIDL 就没有办法复刻**。
所以这一版做的是「同一件事的可插拔实现」，而不是假装接通：

| 层 | 做什么 |
|---|---|
| `vehicle/VehicleData.kt` | 1 秒轮询 + 主线程回调 + 本次行程累计（里程差 / 时长 / 功率对时间积分 ÷ 里程 = 平均电耗） |
| `vehicle/CarPropertySource.kt` | 反射调用标准 `android.car.CarPropertyManager`；只按属性**名字**认（`VehiclePropertyIds.toString`），**不按值域猜**——否则 150 既可能是电压也可能是车速 |
| `vehicle/VehicleProbe.kt` | 诊断：android.car 是否可用 / ServiceManager 里所有「车」相关服务（**连 binder 接口描述一起打**，接口描述就是写客户端要的 AIDL 名）/ `getprop` 里电压电流电量相关行 |

- 每个反射调用都 `runCatching`，读一次失败就把该属性拉黑，不会再每秒刷异常；
- 一律拿不到就 `--`，**绝不拿车机自己的 12V 电源电流冒充动力电池**。

### 还差一步：实车跑一次
设置页 →「车辆」→「打印车辆诊断」，`logcat -s VehicleProbe CarProperty` 会输出：

```
android.car: 可用/不可用
候选服务 N 个 · xxx(xxx.xxx.IVehicle…)
系统属性: [xxx.voltage]: […]
```

把这行发回来就能定死两件事：① 这辆车走的是标准 `android.car` 还是私有服务（后者要按接口描述补 AIDL 客户端）；
② 那四个 vendor 属性 ID 各自对应什么物理量。

在那之前，设置页留了一个**默认关闭**的「实验：把 vendor 属性当瞬时功率」
（`0x2160e003` 是 FLOAT，参照版本在能耗模块里轮询它，但含义没有公开定义）。
确认无误再打开——猜错会把车速显示成 kW。

## 6. 实测（adbtest 1920×1080 / 240dpi）

| 项 | 结果 |
