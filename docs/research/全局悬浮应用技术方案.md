# 全局悬浮应用技术方案（对照氢桌面 / 菱粉桌面）

> 场景：把整个车机桌面做成一个悬浮层，浮在别的应用之上，并且**在浮窗里能真交互**（点按钮、拖地图、放音乐），
> 而不是只显示一张截图。
> 参考样本：`com.mcar.auto`（氢桌面 1.3.1.3，清单见 `desk/pbt_manifest.txt`）。
> 本文只讨论机制与边界，不涉及绕过系统授权的做法。

---

## 0. 先分清三种"悬浮"，能力完全不同

| 层级 | 浮窗里显示什么 | 能真交互吗 | 普通第三方应用能做吗 |
|---|---|---|---|
| **A. 悬浮自己的 UI** | 本应用的 View 树（时钟/卡片/按钮/地图 SDK 的 MapView） | ✅ 触摸、按键、输入法都正常 | ✅ 只要 `SYSTEM_ALERT_WINDOW` |
| **B. 悬浮别人的画面（只读）** | `MediaProjection` 抓屏镜像 | ❌ 只能看，点不到（点击落在浮窗自己身上） | ✅ 但每次启动要用户点"开始录制" |
| **C. 悬浮别人的画面（可交互）** | 别的 App 的 Activity 跑在自建虚拟屏上 | ✅ 画面真实时、触摸可注入 | ❌ 需要系统签名/priv-app/注入 |

氢桌面截图里"高德地图铺在浮窗里还能拖动"，是 **C**；它的卡片、按钮、音乐控制，是 **A**。
两者在系统里是两套完全不同的机制，**不要混为一谈**。

---

## 1. 氢桌面实际是怎么做的（按其清单实证）

`com.mcar.auto` 1.3.1.3 的关键组件：

| 组件 | 标签 / 类型 | 作用 |
|---|---|---|
| `MainActivity` | 桌面主界面 | 常规 Activity 形态 |
| `service.FloatButtonService` | 普通 Service | 悬浮层宿主（配合 `SYSTEM_ALERT_WINDOW`） |
| `activity.VirtualDisplayActivity` | Activity | **虚拟屏容器**：把别的应用的活动渲染进自己的 Surface |
| `service.MediaControllerService` | 通知使用权，标签「**自动化服务**」 | `NotificationListenerService` + `MediaBrowserService`：读通知、接媒体按键、拿歌曲信息 |
| `service.KeyMonitorService` | 无障碍，标签「氢桌面(方控辅助)」 | 方向盘/物理按键监听 |
| `service.accessibilityService` | 无障碍，标签「氢桌面(**模拟返回/悬浮模拟圆角**)」 | 给虚拟屏里的内容注入返回键；给系统窗口补圆角 |

它声明的关键权限（全部是 signature/privileged 级，普通安装拿不到）：

```
SYSTEM_ALERT_WINDOW            ← 「在上层显示」弹窗对应的那个
BIND_NOTIFICATION_LISTENER_SERVICE ← 「自动化」弹窗对应的那个
ADD_TRUSTED_DISPLAY            ┐
INJECT_EVENTS                  ├ 虚拟屏 + 触摸注入三件套（C 层能力的真正来源）
MANAGE_ACTIVITY_STACKS         ┘
MANAGE_ACTIVITY_TASKS / GET_TASKS / REORDER_TASKS
CHANGE_CONFIGURATION / WRITE_SECURE_SETTINGS / DUMP / READ_LOGS
PACKAGE_USAGE_STATS / MEDIA_CONTENT_CONTROL / BIND_APPWIDGET
```

结论：**氢桌面不是"靠悬浮窗权限把高德塞进浮窗"的**。悬浮窗权限只负责"能画在别人上面"；
把高德画进来靠的是虚拟屏 + 特权权限；两个无障碍服务是补丁（返回键、方控、圆角）。

## 2. 「在上层显示」（SYSTEM_ALERT_WINDOW）到底给了什么

- 它是 **appop**，不是运行时权限：只能 `Settings.canDrawOverlays()` 读、跳 `ACTION_MANAGE_OVERLAY_PERMISSION` 让用户点开关；
- 有它才能 `WindowManager.addView(view, TYPE_APPLICATION_OVERLAY)`；没它 → `BadTokenException: Unable to add window — permission denied`；
- 它**只决定"能不能画在别人上面"**，与"能不能交互"无关：交互取决于窗口 flag（见 3.2）；
- 它**不能**让别的应用的内容出现在你的窗口里 —— 这是最容易被误解的一点。

申请路径（工程内已实现，见 `map/MapOverlayPermission.kt`）：

```
Settings.canDrawOverlays() → 已授权
  ↳ 有 su：appops set <pkg> SYSTEM_ALERT_WINDOW allow
  ↳ 有系统页：ACTION_MANAGE_OVERLAY_PERMISSION(package:<pkg>)
  ↳ 都没有：给出 adb 命令
```

## 3. 「自动化」（通知使用权）到底给了什么

截图里的「通知使用权 → 氢桌面 / 自动化服务」就是 `MediaControllerService`（`NotificationListenerService`）。

它提供的是**数据与触发**，不是绘制能力：

| 能力 | API | 氢桌面拿它干嘛 |
|---|---|---|
| 读所有通知（标题/文本/按钮） | `onNotificationPosted` | 场景自动化：识别导航/来电/媒体，切换桌面布局 |
| 媒体通知与播放控制 | `Notification.MediaStyle` + `MediaSessionManager` | 补齐歌曲名/封面/播放状态；通知上的播放键 |
| 媒体库浏览 | `MediaBrowserService` / `MediaBrowserCompat` | 列表、切歌 |
| 通知里的动作按钮 | `Notification.Action` + `PendingIntent` | 免开 App 直接控制 |

**它和悬浮没有因果关系**：不给通知使用权，浮窗照样能画、能点，只是数据少一半。
反过来，给了通知使用权也不会凭空获得浮窗能力。

另外两个容易混的授权：

| 授权 | 系统页面 | 作用 |
|---|---|---|
| 通知使用权 | 设置 → 通知 → 通知使用权 | 读通知、媒体信息、通知按钮 |
| 无障碍服务 | 设置 → 无障碍 | 读界面节点、模拟点击/返回/滑动、监听物理键 |
| 悬浮窗 | 设置 → 应用 → 显示在其他应用上层 | 画在别人上面 |

## 4. 方案 A：把自己的整个应用做成悬浮（普通应用可落地）

> 这是"整个桌面浮在别的应用之上，且浮窗内一切都能点"的正解。地图用**地图 SDK 的 MapView**（自己进程内的 View），
> 天然可拖动、可缩放 —— 不需要虚拟屏、不需要注入。

### 4.1 宿主：前台 Service，不是 Activity

```
OverlayHostService (foreground)
  └── WindowManager
        └── root(自绘/圆角/阴影)
              ├── TopBar
              ├── MapCard  → AMap MapView / 自绘
              └── RightColumn(时间/音乐/行程/负载)
```

- 为什么是 Service：Activity 有任务栈与生命周期，按 Home/切换应用会暂停甚至销毁；Service 持有的窗口不随 Activity 走；
- Android 8+ 必须 `startForeground()`（否则后台一会儿就被杀）；Android 14 还要声明 `foregroundServiceType`；
- 窗口状态要自己管：什么时候显示、什么时候收起（见 4.4）。

### 4.2 窗口参数：四态

| 形态 | flags | 效果 |
|---|---|---|
| 纯展示 | `NOT_FOCUSABLE｜NOT_TOUCHABLE` | 不抢焦点、不吃触摸（适合后视镜类信息层） |
| 可点（推荐默认） | `NOT_FOCUSABLE` | 触摸进窗口，桌面/下层应用仍持焦点，**不弹输入法、不破坏下层沉浸式** |
| 可交互 + 可输入 | 去掉 `NOT_FOCUSABLE`，加 `NOT_TOUCH_MODAL` | 能收按键、弹输入法；代价是抢焦点，下层应用失焦 |
| 可拖动 | 上述任一 + 自己处理 `ACTION_MOVE` 改 `params.x/y` | 拖动不是 flag，是手写手势 |

补齐：`TYPE_APPLICATION_OVERLAY`、`PixelFormat.TRANSLUCENT`、`FLAG_LAYOUT_IN_SCREEN`、
`FLAG_HARDWARE_ACCELERATED`、`windowAnimations = 0`（车机上别让系统做窗口动画）。

关于输入法的坑：`FLAG_ALT_FOCUSABLE_IM` 的语义是"**反转** NOT_FOCUSABLE 对输入法的影响"——
可聚焦窗口加上它，等于告诉系统"我不需要输入法"，可以避免一聚焦就弹键盘。要真输入时才去掉。

### 4.3 浮窗里的交互细节

| 交互 | 怎么做 | 坑 |
|---|---|---|
| 点击/滑动 | 普通 View 事件，无需额外处理 | 若窗口带 `NOT_TOUCHABLE` 则全部穿透，收不到 |
| 返回键 | 窗口可聚焦时，`root.dispatchKeyEvent` 里拦 `KEYCODE_BACK` | 浮窗不是 Activity，系统不会替你 pop；氢桌面正是用无障碍"模拟返回"补这一环 |
| 输入法 | 可聚焦 + 不加 `ALT_FOCUSABLE_IM`，并 `adjustResize`/自己算 insets | 浮窗不受 Activity 的 `windowSoftInputMode` 管理 |
| 拖动 | `ACTION_DOWN` 记起点，`ACTION_MOVE` 改 `x/y`，`ACTION_UP` 吸附 | 必须夹在屏幕边界内；多指要取 `pointerId` |
| 缩放 | 改 `params.width/height` 后 `updateViewLayout` | 高频调用要节流 |
| 圆角/阴影 | `outlineProvider + clipToOutline`，或自绘 | **系统窗口没有父布局可裁**，只能自己来（氢桌面"悬浮模拟圆角"就是这个原因） |
| 焦点 | 非必要不聚焦 | 一聚焦，下层应用的沉浸式失效、系统栏会冒出来（本项目已实测） |

### 4.4 可见性状态机

浮窗不能"一直挂着"，否则会压在设置页、系统弹窗、别的应用上。建议单一事实来源：

```
visible = serviceAlive && foregroundApp != self && !screenOff && !keyguardShowing && pageWantsOverlay
```

触发点：`onResume/onPause`、`UsageStats` 前台应用变化、`ACTION_SCREEN_OFF/ON`、`ACTION_USER_PRESENT`、
`Configuration` 变化（分辨率/密度）、`onTaskStackChanged`（有特权时）。

### 4.5 性能（MT8666 这类车机）

- 别用 `BlurView`/多层模糊，掉帧明显；用半透明纯色 + 1px 描边；
- 地图用 `TextureView` 或 SDK 自带 `MapView`，避免 `SurfaceView` 在窗口层级变化时黑屏；
- 高频刷新（歌词 150ms、进度）只在可见时跑，锁屏/后台停掉；
- 浮窗尺寸变化后立刻 `requestLayout`，避免整窗重绘风暴。

### 4.6 落到本项目：改造清单

1. 新增 `OverlayHostService`（前台服务），持有 `WindowManager` 与根容器；
2. 把 `HomeFragment` 里的渲染逻辑抽成 `HomeController`（纯 View 级，不依赖 Fragment）——
   Activity 与 Service 两种宿主复用同一套 UI；
3. `MapOverlayWindow` 已有的窗口策略（四态 flag、圆角裁切、可见性状态机）直接复用，只是容器从"地图卡"放大到"整屏"；
4. 地图：`OverlayMapView.setMapContentView(AMap MapView)`，删掉演示图层；
5. 返回键：`root.dispatchKeyEvent` 拦 BACK → 优先退回桌面首页，其次收起浮窗；
6. 入口：设置里加"悬浮模式（浮在其它应用之上）"开关，开启时 `startForegroundService` + 请求悬浮窗权限。

## 5. 方案 C：一定要把"别的应用"浮进来还能点（氢桌面那条路）

前提：**系统签名 / priv-app / ROM 白名单**。普通安装必然 `Permission Denial`（本项目已实测失败）。

```kotlin
// 1) 自己开一块虚拟屏，输出到窗口里的 SurfaceView
val vd = displayManager.createVirtualDisplay(
    "embed", w, h, dpi, surface, DisplayManager.VIRTUAL_DISPLAY_FLAG_PUBLIC
)

// 2) 把目标 Activity 拉到这块屏上（需要 MANAGE_ACTIVITY_STACKS 等）
val opts = ActivityOptions.makeBasic()
opts.javaClass.getMethod("setLaunchDisplayId", Int::class.java).invoke(opts, vd.display.displayId)
startActivity(intent, opts.toBundle())

// 3) 触摸注入回目标屏（需要 INJECT_EVENTS）
val e = MotionEvent.obtain(downTime, eventTime, action, x, y, 0)
e.setSource(InputDevice.SOURCE_TOUCHSCREEN)
inputManager.injectInputEvent(e, InputManager.INJECT_INPUT_EVENT_MODE_ASYNC)
```

难点：坐标映射、事件时间戳、多指、旋转、焦点与返回键（返回键要注入到虚拟屏，不能只在自己窗口里消费）——
这就是氢桌面为什么还要挂两个无障碍服务。

## 6. 授权申请速查

| 授权 | 判断 | 申请 | 有无回调 |
|---|---|---|---|
| 悬浮窗 | `Settings.canDrawOverlays()` | `ACTION_MANAGE_OVERLAY_PERMISSION` | ❌ 只能 `onResume` 复检 |
| 通知使用权 | `NotificationManagerCompat.getEnabledListenerPackages()` | `ACTION_NOTIFICATION_LISTENER_SETTINGS` | ❌ 同样靠复检 |
| 无障碍 | `AccessibilityManager.getEnabledAccessibilityServiceList()` | `ACTION_ACCESSIBILITY_SETTINGS` | ❌ 复检 |
| 前台服务 | — | `startForeground()` + 通知渠道 | ✅ |

常见误区：

1. "开了悬浮窗就能显示别的应用" —— 不能，只能显示自己的 View；
2. "通知使用权是悬浮的前置条件" —— 不是，它只提供数据；
3. "无障碍能替代悬浮窗" —— 不能，无障碍不能画持续的自定义浮层（只能用 `TYPE_ACCESSIBILITY_OVERLAY`，
   且只对无障碍服务可见，仍受系统限制）；
4. "targetSdk 高一点更兼容" —— Android 12+ 对不透明浮层有 **untrusted touch** 拦截（触摸不再穿透到下层），
   Android 14 又收紧前台服务类型。车机停在 28 是刻意的。

## 7. 建议路线（针对本项目）

| 目标 | 路线 | 代价 |
|---|---|---|
| 桌面整体悬浮 + 真交互（含真地图） | **方案 A**：前台 Service + 整屏 overlay + 地图 SDK MapView | 1~2 天，无特权 |
| 浮窗里看"高德车机版"并点它 | 方案 C | 必须系统签名/priv-app，普通安装做不到 |
| 只想在浮窗里"看"别的应用 | 方案 B（MediaProjection 镜像） | 只读、每次启动要授权、隐私提示无法去掉 |

结论：**先把 A 做扎实**（自己的 UI + 真地图 SDK），这是唯一"零特权 + 真交互"的组合；
C 只在有 ROM 合作或 priv-app 部署时才有意义。

## 附录 A · 实测更正（2026-10-31，emulator 1920×1080 / Android 9）

### A.1 零权限能做到什么

`ActivityOptions.setLaunchWindowingMode(5) + setLaunchBounds(rect)` 把高德摆进地图卡矩形，
**实测通过**（本工程 `map/FreeformMapController.kt`）：

- 画面是高德自己渲染的，实时、无延迟；
- 点地图会真的弹出 POI 卡片（"北京利生体育商厦 / 34 米 / 电话"），说明触摸直落高德，
  **不需要 INJECT_EVENTS**；
- 我们只画一圈描边（`FreeformFrameOverlay` 的透明窗口，`FLAG_NOT_TOUCHABLE`），
  再加一层可触摸的标题栏盖住 AOSP 的 ⛶/✕。

### A.2 零权限做不到什么

| 期望 | 自由窗口方案 | 原因 |
|---|---|---|
| 切页时地图自动消失 | ✗（只能把它缩成 1×1 挪走，是打补丁） | 它是**独立任务**，不属于我们的 View 树 |
| 完全没有系统标题栏 | △（要靠浮层盖） | caption 是系统给它的 decor，应用侧改不了别人的窗口 |
| 和卡片一起做位移动画 | ✗ | 同上 |

结论：**"切页即隐藏 + 无系统栏 + 真交互" 三件事同时成立，只有一个实现——
把别的应用渲染进自己的 View 树（VirtualDisplay / ActivityView）。**
ActivityView 是 API 29+，车机是 9，只能 VirtualDisplay，而它要 `CAPTURE_VIDEO_OUTPUT` 等
signature 级权限。

### A.3 如果氢桌面确实没有特权，怎么解释

三条自查命令（在你车上跑，30 秒出结论）：

```bash
# ① 它是不是预装的系统应用
adb shell pm path com.mcar.auto        # 路径在 /system/priv-app/ 下即是
# ② 它到底拿到了哪些 signature 权限
adb shell dumpsys package com.mcar.auto | grep -E "CAPTURE_VIDEO_OUTPUT|INJECT_EVENTS|MANAGE_ACTIVITY_STACKS|ADD_TRUSTED_DISPLAY" -A1
# ③ 有没有运行时注入（frida / 自改 system_server）
adb shell "ps -A | grep -i frida"; adb shell getprop | grep -i "ro.debuggable\|ro.secure"
```

只有两种可能：①/② 命中 → 它是特权应用（车机厂商预装，用户无感）；
③ 命中 → 走了菱粉桌面那套 frida 注入 system_server 的路子。
这两者之外，Android 9 上没有第三条路能把别的应用画进自己的 View 树。
