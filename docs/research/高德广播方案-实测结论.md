# 广播控制高德悬浮窗 —— 实测结论

> 被测应用：高德车机版 `com.autonavi.amapauto` 9.1.0.600087（targetSdk 23）
> 设备：emulator-5554 · Android 9 / API 28
> 工具：`probe/AmapSignalActivity`（收 + 发广播）

## 一、结论

`com.autonavi.plus.showmap` / `closemap` 这套广播，**对这台设备上这个版本的高德不成立**。

不是因为权限没给 —— 恰恰相反，高德的 `SYSTEM_ALERT_WINDOW` 是 `allow`，
它有能力画悬浮窗；是它**根本不认这个指令**。

## 二、四条证据

### 2.1 清单里没有这个 action

`aapt dump xmltree` 解析高德 9.1.0 的 `AndroidManifest.xml`，共 140 条 action、10 个 receiver。
搜 `showmap` / `closemap` / `autonavi.plus`，**零命中**。

它真正声明的是这些：

```xml
<receiver android:name="com.autonavi.amapauto.adapter.internal.AmapAutoBroadcastReceiver"
          android:exported="true">
    <intent-filter>
        <action android:name="AUTONAVI_STANDARD_BROADCAST_RECV" />
        <action android:name="com.autonavi.amapauto.receiver_test" />
        <action android:name="FLY.ANDROID.NAVI.MSG.SENDER" />
        <action android:name="com.neusoft.action.carmodechange" />
        <action android:name="com.incall.action.carmodechange" />
        <action android:name="com.autonavi.xm.action.NAVIGATE" />
    </intent-filter>
</receiver>
```

### 2.2 发出去没人收

```bash
adb shell am broadcast -a com.autonavi.plus.showmap -p com.autonavi.amapauto \
    --ei x 100 --ei y 200 --ei w 800 --ei h 600
# Broadcast completed: result=0

adb shell am broadcast -a com.autonavi.plus.closemap -p com.autonavi.amapauto
# Broadcast completed: result=0
```

logcat 里没有任何 receiver 被触发的痕迹，屏幕无变化。

### 2.3 这个版本压根没有「悬浮窗」

把 APK 的 dex 抽出来 `strings | grep 悬浮窗`：`0` 命中。

一个真要提供悬浮窗的功能，至少在字符串资源里会留下「悬浮窗」三个字。

### 2.4 界面上按了也没反应

用探针页的 `发 showmap` 按钮（带真实坐标 `x=960 y=210 w=890 h=800`）发一次，
`dumpsys window windows` 里高德的窗口数量不变，屏幕上没有新窗口。

## 三、更根本的问题：坐标不能跨进程给

这一点比"action 不存在"更要紧 —— 就算某个版本真的响应 `showmap`，`x/y/w/h` 也未必有意义。

**Android 里没有「A 应用设置 B 应用窗口位置」这种能力。**

窗口的 `x / y / width / height` 存在 `WindowManager.LayoutParams` 里，而这份对象属于
**创建窗口的那个进程**。`WindowManagerService` 只接受来自窗口所有者的布局更新请求。
跨进程能传的只有 `Intent` 的数据（字符串、数字、Parcelable），它不会自动变成对方的窗口参数。

所以「广播传坐标」如果要生效，必须是对方应用**自己主动实现**：

```
收到 action → 读 extras["x"] → 自己的 LayoutParams.x = x → updateViewLayout()
```

这是它自愿实现的私有协议，不是系统能力。也就是说：

- 它支持哪些 key、要不要 `setPackage`、是 `x` 还是 `EXTRA_X`，全靠猜；
- 换一个版本就可能变；
- 不能作为 Launcher 的可靠基础。

想验证某个 APK 到底支不支持，只有两条判据：**对方的 logcat 有没有反应**、**屏幕上有没有窗口出现**。
`sendBroadcast()` 永远不返回"对方收到了吗"。

## 四、但你说对了一半：反方向的广播是真的

高德确实在持续往外发广播，实测原样：

```
#24  AUTONAVI_STANDARD_BROADCAST_SEND  12:08:36.483
     EXTRA_GEOLOCATION = 0
     KEY_TYPE = 12205                         ← 每秒一条，心跳

#7   AUTONAVI_STANDARD_BROADCAST_SEND  12:06:41.032
     EXTRA_STATUS_DETAILS = -1
     EXTRA_STATE = 40
     KEY_TYPE = 10019                         ← 状态位
```

字段名就是这些，没有美化过：`KEY_TYPE` / `EXTRA_GEOLOCATION` / `EXTRA_STATE` / `EXTRA_STATUS_DETAILS`。

导航中应该还会出现 `KEY_TYPE=10001`（带路名、剩余距离、转向图标），
但这台模拟器没有 GPS 和路线，触发不了 —— 你在车上导一次航，探针页会直接把完整字段列出来。

**这条路的用途**是：Launcher 拿到导航状态，画在自己的卡片上（路名、剩余距离、转向箭头），
而不是控制高德的窗口。前者可行，后者不可行。

## 五、工具：高德广播探针

入口：桌面 → 设置 → 地图 → **「高德广播探针」**，或

```bash
adb shell am start -n com.lf.launcher/.probe.AmapSignalActivity
```

五个按钮：

| 按钮 | 作用 |
|---|---|
| 清空 | 清列表 |
| 暂停 / 继续 | 停收，方便截图 |
| **发 showmap** | 按当前屏幕右半区算 x/y/w/h 发一次，看有没有窗口出现 |
| 发 closemap | 发关闭 |
| 让高德发一次 | 把高德拉到前台，通常就开始发状态广播 |

每条广播卡片上把 `extras` 的**所有 key 原样列出**，不做字段猜测 —— 换一台车、换一个版本，
你需要看到的是真实数据，不是别人总结的字段表。

## 六、那「地图出现在卡片位置」到底怎么办

广播这条路关掉之后，剩下的还是之前那张表：

| 方案 | 画面 | 触摸 | 普通安装可行 |
|---|---|---|---|
| **地图 SDK 自绘**（MapView 放进卡片） | 自己画 | 原生 | ✅ |
| MediaProjection 抓屏 | 真镜像 | ✗ | ⚠️ 能看不能碰 |
| VirtualDisplay + 注入 | 真镜像 | ✅ | ❌ 需特权 |
| 系统自由窗口摆到卡片位置 | 真窗口 | ✅ | ⚠️ 能画能点，但切页不跟着走、带系统标题栏 |
| 广播控制高德悬浮窗 | — | — | ❌ 本文证否 |

要注意：**前四种里，只有第一种能把地图真正"长"在布局里**。其余三种本质都是"在卡片位置摆一个别的窗口"，
一旦页面切换、列表滚动，就得靠外部逻辑去追。
